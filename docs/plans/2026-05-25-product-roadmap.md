# PixelReel 后续开发路线图

> **目标：** 明确 PixelReel 在基础功能完成后的后续开发方向，避免继续无序堆功能，把项目推进到“长期可用的个人影剧游资料库”。
>
> **结论：** 下一阶段优先做数据质量、记录详情和同步工作台，而不是优先扩展多用户或继续横向接更多 Provider。

## 当前判断

PixelReel 当前已经完成了个人影剧游记录平台的核心闭环：

- 电影、电视剧、游戏三类内容的基础 CRUD
- 电影、电视剧、游戏的多来源搜索
- Trakt、Steam、Xbox、PSN、豆瓣等来源导入
- 混合记录库、时间线、操作日志、Showcase、Analytics
- JWT 登录、系统设置、任务进度、Toast 和撤销能力

项目已经过了“补基础页面”和“补基础接口”的阶段。继续增加零散页面或 Provider 的边际收益会下降，真正影响长期使用体验的问题会集中在：

- 多来源数据是否可信
- 导入后记录是否需要人工修正
- 重复记录是否容易发现和合并
- 单条记录是否有足够完整的详情页
- 同步过程是否足够稳定、可见、可重试
- 项目结构是否能支撑继续演进

因此，后续开发应该从“功能覆盖”转向“数据可信 + 使用闭环 + 可维护性”。

## 推荐优先级

### 1. 数据质量工作台

这是当前收益最高的方向。

PixelReel 已经接入了豆瓣、TMDB、Trakt、RAWG、Steam、Xbox、PSN 等来源，下一步的核心问题不是“还能接什么”，而是“多来源数据如何融合、修正和长期维护”。

建议实现：

- 重复记录检测：按外部 ID、标题、年份、平台等规则识别疑似重复。
- 记录合并：允许把重复电影、剧集或游戏合并为一条记录。
- 缺字段检测：缺封面、缺上映日期、缺简介、缺评分、缺外部 ID。
- 批量修复：批量触发 TMDB、RAWG、Steam 等来源回填。
- 导入后 Review 队列：新导入记录先进入待确认状态，用户可以批量接受、修正或忽略。
- 来源字段对比：展示豆瓣、TMDB、IMDb、Trakt 等来源的原始字段和当前显示字段。

这个方向会把项目从“能导入数据”推进到“能维护一套可信的个人资料库”。

### 2. 记录详情页

当前记录库更像列表工作台，适合快速筛选、评分和写短评，但长期使用需要单条记录的完整页面。

建议新增：

- `/library/:category/:id` 详情页
- 电影、电视剧、游戏共用的详情页骨架
- 来源 ID、外部链接、封面、简介、年份、状态、评分、短评
- 游戏展示平台、游玩时长、成就总数、已解锁数量
- 影视展示导演、演员、类型、IMDb/TMDB/豆瓣评分等信息
- 从详情页触发刷新元数据、合并重复、重新匹配来源
- 与操作日志联动，展示这条记录的变更历史

详情页会成为后续数据质量、同步修复、深度分析的入口。

### 3. 同步中心

目前导入能力很多，但更像 API 能力。下一步应该把它产品化成一个稳定的同步中心。

建议新增 `/sync` 页面：

- Steam、Xbox、PSN、Trakt、豆瓣分来源展示同步状态
- 显示上次同步时间、导入数量、更新数量、失败数量
- 支持一键同步、增量同步、取消任务、查看日志
- 配置缺失时直接跳转到 Settings 对应配置项
- 同步完成后进入 Review 队列，而不是静默沉入记录库

项目已有任务管理、Toast、Settings、Activity Log，这些能力可以复用。同步中心能明显提升日常使用体验。

### 4. 个人洞察增强

Analytics 和 Showcase 已经打好了基础，后续可以做更个人化的洞察，而不是只做统计图。

可选方向：

- 年度报告：按年份生成影剧游总结。
- 偏好画像：高评分类型、常玩平台、常看年份、最密集月份。
- 随机推荐增强：支持按状态、类别、评分、平台筛选随机推荐。
- 待看/待玩队列：从 WANT 状态中生成优先级列表。
- 回顾模式：展示“去年今天”“这个月历史记录”等轻量回忆功能。

这些功能应建立在数据质量稳定之后，否则分析结果容易失真。

### 5. 维护性建设

项目已经有 Express 后端、旧 Java 后端、豆瓣采集子项目、前端和多份计划文档。后续继续扩功能前，需要逐步收敛维护成本。

建议：

- 明确 Express + Prisma 是唯一主路径。
- Java 后端保留为 legacy 参考，不再承接新功能。
- 为导入、去重、记录库聚合、Activity undo 补最小测试。
- 清理或隔离敏感本地文件，例如 `.env.backup`。
- 整理 README 和 `docs/PROJECT_STATUS.md`，避免状态描述冲突。
- 对高风险脚本和导入流程补运行说明。

维护性不是第一阶段的产品亮点，但会决定项目后续能不能稳步演进。

## 阶段路线图

### Phase 1: 数据健康

目标：让库里的数据可检查、可修复、可合并。

建议交付：

- 数据健康页面
- 缺字段检测
- 疑似重复检测
- 单条/批量元数据刷新
- 初版合并流程

验收标准：

- 用户可以知道当前库里哪些记录有问题。
- 用户可以批量修复封面、简介、日期等常见缺口。
- 用户可以处理明显重复记录。

### Phase 2: 记录详情

目标：为每条记录建立稳定的深度入口。

建议交付：

- 统一详情页路由
- 影视和游戏差异化字段展示
- 来源字段与显示字段对比
- 记录级 Activity Log
- 详情页触发刷新、合并、重匹配

验收标准：

- 从记录库、时间线、活动日志、Showcase 都能进入详情页。
- 用户能在详情页理解一条记录来自哪里、当前字段为何如此。

### Phase 3: 同步中心

目标：把导入能力转化为可重复使用的同步流程。

建议交付：

- `/sync` 页面
- 各来源配置状态检查
- 同步任务启动、取消、进度、结果
- 同步失败原因展示
- 同步后 Review 队列

验收标准：

- 用户不需要记 API 路径就能完成日常同步。
- 同步失败时能知道是配置问题、网络问题还是来源数据问题。

### Phase 4: 个人洞察

目标：让 PixelReel 从记录工具升级为个人回顾工具。

建议交付：

- 年度报告
- 偏好画像
- 待看/待玩优先队列
- 随机推荐增强
- 可分享或可导出的报告截图

验收标准：

- 用户能从自己的记录中得到有意义的回顾和下一步行动建议。

### Phase 5: 工程收敛

目标：降低后续维护成本。

建议交付：

- Express 主路径文档统一
- legacy Java 后端说明
- 最小测试体系
- 敏感文件清理
- 高风险导入流程说明

验收标准：

- 新功能默认只进入 Express 后端。
- 关键数据流程有测试或可重复验证脚本。
- README、项目状态文档和实际代码不再互相矛盾。

## 暂缓事项

### 多用户系统

暂缓。

项目当前定位是个人影剧游资料库，多用户登录、租户隔离、权限体系会显著增加复杂度，但不会直接改善个人使用体验。

可以保留：

- 单用户登录
- 改密码
- 本地部署安全提示
- 备份与恢复

不建议近期做：

- 多用户注册
- 公共主页
- 家庭共享库
- 权限矩阵
- 团队或租户模型

### 继续大量增加 Provider

暂缓。

Provider 已经足够多，继续接新来源之前，应先解决数据融合和修复体验。否则来源越多，重复和冲突越多。

### 复杂推荐系统

暂缓。

在数据质量和详情页没有稳定之前，不建议做复杂推荐算法。可以先做规则型推荐，例如：

- 高评分未回顾
- WANT 中随机挑选
- 同平台未完成游戏
- 同类型高评分作品

## 推荐下一步

下一步建议从 **数据质量工作台 + 记录详情页** 开始。

原因：

- 两者复用现有数据模型，不需要大规模 schema 重构。
- 它们直接解决长期使用中最痛的问题。
- 后续同步中心、年度报告、推荐功能都依赖更可信的数据。
- 它们能把现有导入、搜索、日志、分析能力串成更完整的产品闭环。

第一批可以拆成三个小里程碑：

1. 新增记录详情页，只读展示现有字段。
2. 新增数据健康接口，返回缺封面、缺日期、缺简介、疑似重复数量。
3. 在详情页加入刷新元数据和疑似重复入口。

这样可以快速获得可见成果，同时避免一开始就陷入复杂合并逻辑。
